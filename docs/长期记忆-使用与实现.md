# 长期记忆：使用与实现说明

本文是 XimoAgent **长期记忆**能力的完整说明：怎么开、数据在哪、引擎里是怎么实现的、
有哪些有意为之的取舍、出问题怎么查。

> 想直接用：跳到「二、快速开始」。想理解实现：看「四、实现结构」与「五、运行时行为」。
> `docs/长期记忆-mem0.md` 仍是 **mem0 自托管路线**的专项参考；本文覆盖两条路线并说明
> 如何选择。

---

## 一、这是什么，和 mem0 什么关系

长期记忆 = 让工作台跨会话记住用户的偏好与结论，并在后续对话里自动召回。

引擎提供**两种可切换的后端**，共用同一套配置、同一条引擎链路（召回注入、收尾回填、
`memory` 工具），切换只改 `backend`：

| | `embedded`（进程内，推荐） | `mem0`（自托管服务） |
| --- | --- | --- |
| 依赖 | **无**（引擎自带 SQLite） | Docker + Postgres(pgvector) + 抽取用 LLM + **额外的向量模型** |
| 数据位置 | 本机文件 `<BaseDir>/data/memory.db` | 你自托管的 Postgres |
| 写入 | **原样存这一轮问答** | LLM 抽取成"事实" |
| 检索 | **词法**（中文单字+二元组，英文按词） | 向量语义检索 |
| 同义改写 | 命中弱（"深色界面" 命不中 "暗色主题"） | 命中强 |
| 部署成本 | 打开开关即可 | 一套 compose + 两个模型 |

**为什么做进程内后端**：记忆是增强能力，不是运行前提。为它引入 Docker + Postgres +
一个必须常驻的向量模型（DeepSeek 没有 embeddings 接口，必须另配 Ollama / 硅基流动 /
DashScope），与"让工作台记住我说过的偏好"这个目标不成比例。

**什么时候该用 mem0**：需要更强的语义召回、多人共享一套记忆、或要一个可视化 dashboard。

## 二、快速开始

### 1. 打开两个开关

编辑 `<BaseDir>/config.json`（Windows 通常是 `%APPDATA%\ximo-agent\config.json`，
可用 `XIMO_HOME` 覆盖 BaseDir）：

```jsonc
{
  "feature_flags": { "memory.mem0": true },   // 一级开关：整机/整环境熔断
  "memory": {
    "enabled": true,                          // 二级开关：用户级
    "backend": "embedded",                    // 可省略；留空时按 endpoint 推断
    "user_id": "ximo-user",                   // 记忆归属：跨会话共享的就是这一维度
    "agent_id": "ximo-agent",
    "top_k": 5,                               // 每次最多召回几条
    "recall_max_chars": 1200,                 // 注入提示词的记忆块字符上限
    "write_back": true,                       // 三态：不写这个键 = 默认开启
    "timeout": 700000000,                     // 纳秒 = 700ms，召回等待上限
    "extract_timeout": 30000000000,           // 纳秒 = 30s，回填上限
    "queue_depth": 32,
    "max_inflight": 2
  }
}
```

要点（都是踩过的坑）：

- **两个开关都要开**：`feature_flags["memory.mem0"]` 是一级熔断（可不改用户配置就整条关掉），
  `memory.enabled` 是二级。只开一个不生效。
- **`backend` 可以省略**：给了 `endpoint` 走 mem0，没给就走进程内。所以"只想用自带后端"
  的最短写法就是上面这段（`backend` 写不写都行）。
- **时长单位是纳秒**：与本文件其它段（`supervisor` / `ipc`）一致，混用单位更容易出错。
- **`write_back` 是三态**：不写这个键 = 默认开启；写 `false` 才是关。把它当普通 bool
  会得到"记忆只读不写"，很难查。
- 进程内后端**不需要** `endpoint` / `secret_ref`。

### 2. 构建与验证

```bash
# Windows（cmd）
set GOROOT=C:\ximo-tools\go          # 或你自己的 Go 安装位置
build.cmd verify                     # 闸门：build + vet + test-short
build.cmd exe                        # 产出 dist\ximo-agent.exe

# 仅记忆相关的测试
go test ./internal/memory/... -count=1
go test ./internal/bootstrap/... -count=1
```

### 3. 验证它真的在工作

进程内后端：

```bash
# 起一次工作台（任意一轮对话即可），然后：
ls "%APPDATA%\ximo-agent\data\memory.db"        # 文件出现了
```

用 `memory` 工具或直接查库确认有条目；重启工作台后再问相关问题时，应能看到注入的
记忆块（日志里搜「长期记忆」）。

mem0 后端（注意 **8888 才是 API**，3000 是 dashboard）：

```bash
curl -s -H "X-API-Key: <key>" http://127.0.0.1:8888/configure
curl -s -H "X-API-Key: <key>" "http://127.0.0.1:8888/memories?user_id=ximo-user&top_k=10"
```

**降级也要验一次**：把后端停掉/改坏，再跑一轮 —— 应当只有一条
「长期记忆召回失败，本轮按「无记忆」继续」的告警，对话完全不受影响。

## 三、数据与隐私

- 进程内后端的数据只有一个文件：`<BaseDir>/data/memory.db`。**删掉它 = 清空全部记忆。**
- mem0 后端的数据在你自托管的 Postgres 数据卷里，本工程不存第二份副本。
- 投递给记忆的内容只有**这一轮的用户提问与模型最终答复**（`Turn.Messages()`），
  不含系统提示词、工具输出、文件内容或任何密钥。
  只投递一轮的原因：引擎每次 run 只拿到当前提示词，会话历史由前端拼在系统提示词里，
  本进程取不回完整原文——**伪造一份它没有的历史才是真正有害的**。
- 进程内后端不外发任何网络请求；mem0 后端只发 `X-API-Key`（**不发** `Authorization: Bearer`：
  mem0 的 `verify_auth()` 会把 Bearer 当 JWT 解析并直接返回，不回退到 X-API-Key，必然 401）。

## 四、实现结构

```
internal/memory/
├── backend.go        后端接口 Backend（消费方定义）+ 后端名字常量
├── embedded.go       进程内 SQLite 后端（表结构、写入幂等、按 user 隔离）
├── lexical.go        词法分词与打分（tokenize / score / rank）
├── client.go         mem0 HTTP 客户端（实现同一接口）
├── service.go        门面：召回注入、回填队列、Stats、后端选择后的统一入口
├── recall.go         「读」路径：把命中的记忆渲染成注入块
├── writeback.go      「写」路径：run 收尾入队 → 后台 goroutine 投递
├── config.go         运行期配置（含 backend 选择与校验）
└── types.go          Message / Record / Turn / Stats

internal/bootstrap/memory.go   装配：按 backend 选后端、注入幂等闸、适配成引擎端口
internal/config/memory.go      config.json 的 memory 段（含 backend 字段）
internal/tool/domains/memory/  memory 工具（让模型能主动 add/search/list/forget）
```

关键接缝：

- **`Backend` 接口由消费方（`internal/memory`）定义**，`*Client`（mem0）与
  `*EmbeddedBackend`（进程内）都满足它。加后端不需要改 `Service` 任何逻辑。
- **`Service` 不再持有具体客户端**：它只认 `Backend`。`Close()` 时若后端实现了
  `io.Closer` 就顺手关掉（进程内后端持有 SQLite 文件句柄，不关会让下次启动拿不到写锁）。
- **进程内后端自带表结构**，不复用引擎的 `migrations/`：引擎 schema 由迁移注册表统一
  管理（版本连续 + checksum 钉死 + 有既定的归属规则），为一个可选特性去动那张注册表
  不成比例；独立成文件还让"清空记忆"变成删一个文件。
- **回填幂等**复用 `tool_idempotency` 表（`memory.extract:<runID>`，TTL 24 小时）：
  同一个 run 无论被收尾多少次（取消、崩溃恢复、重复 finish）都只抽取一次。

## 五、运行时行为

### 召回（读）

- 时机：一次 run 开始前，用本次提示词向记忆后端检索 `top_k` 条。
- 注入位置：作为**独立 system 消息**，放在系统提示词之后、用户消息之前。
- 没命中时**完全不插**（不插空块、不插"暂无记忆"）。
- 超时 `timeout`（默认 700ms）**直接等于每个 run 开始前多出的等待**，因此刻意取小。
- 失败只降级为"这一轮没有记忆"，绝不阻塞、绝不失败一个 run。

### 回填（写）

- 时机：run 收尾时把这一轮问答入队，由 `max_inflight` 个后台 goroutine 投递。
- `extract_timeout`（默认 30s）比召回大两个数量级是有意的：那是"写"，mem0 侧要调一次 LLM。
- 队列满时丢弃并计数（`BackfillDropped`），**不阻塞收尾**。
- 进程内后端的写入是本地 SQLite，毫秒级；同一 user 下内容相同只保留一条
  （按内容哈希去重），所以重复投递不会把库塞满副本。

### 运行计数（`Service.Stats()`）

| 字段 | 含义 |
| --- | --- |
| `RecallCalls` / `RecallHits` / `RecallErrors` | 召回次数 / 命中次数 / 失败次数 |
| `RecallChars` | 累计注入字符数 |
| `BackfillEnqueued` / `BackfillDone` / `BackfillFailed` | 回填入队 / 成功 / 失败 |
| `BackfillSkipped` | **正常现象**：同一 run 被重复收尾时幂等闸只放行一次 |
| `BackfillDropped` | 队列满被丢弃：调大 `queue_depth` / `max_inflight` |
| `LastError` / `LastErrorAt` | 最近一次失败原因（已脱敏，密钥不会出现在里面） |

## 六、取舍与边界（有意为之，别当成故障）

1. **写入不做 LLM 抽取**：进程内后端原样保存这一轮问答。没有 LLM 就不该假装能提炼事实；
   代价是记忆里是原话而不是"用户偏好暗色主题"这种短句，好处是可核查、不会编造。
2. **检索是词法的**：中文按单字 + 相邻二元组打分，英文按单词。关键词对得上就准，
   同义改写命中弱。这是不引入向量模型（及其外部服务）的直接代价。
3. **有界扫描**：单次检索最多扫描该用户最近 2000 条候选，保证查询有界。
   个人记忆量级足够；真要海量记忆，请用 mem0 的向量检索。
4. **单用户维度隔离**：记忆按 `user_id` 隔离；`agent_id` 只随记录保存，不参与过滤。
5. **不做记忆的自动过期/衰减**：需要清理就用 `memory` 工具的 `forget` 或删库文件。

### 想升级成语义检索

只需替换 `internal/memory/lexical.go` 里的打分函数（`tokenize` / `score` / `rank`），
`Service`、`Backend` 接口、配置与注入逻辑都不用动。最省事的落地方式：在服务器或本机
跑 Ollama（`nomic-embed-text` 约 274MB），把 `rank` 换成向量相似度。

## 七、排障

| 现象 | 处理 |
| --- | --- |
| 工作台报「长期记忆召回失败，本轮按无记忆继续」 | 后端不可用：进程内看 `data/` 目录权限；mem0 看服务与 `endpoint`（**8888**，不是 3000） |
| 两个开关都开了却没反应 | 检查 `feature_flags["memory.mem0"]` 是否为 `true`（一级熔断），以及 `memory.enabled` |
| 记忆只读不写 | `write_back` 被显式写成 `false`（三态键） |
| mem0 返回 401 | 只发 `X-API-Key`，**不要**用 `Authorization: Bearer` |
| 写进去了但召回不到（mem0） | **embedder 没配好**：DeepSeek 没有 embeddings 接口，必须另配向量模型 |
| 写进去了但召回不到（进程内） | 词法检索的正常表现：换更接近原话的关键词 |
| mem0 部署起不来 | 上游 compose 的 `.env` 里 `POSTGRES_PASSWORD` 必填；回环绑定要写 `ports: !override` |
| 每轮对话慢 ~700ms | 召回超时被用满：后端响应慢，调小 `timeout` 或查后端 |

## 八、验证证据（哪些测试覆盖什么）

```bash
go test ./internal/memory/... -count=1      # 含进程内后端与后端选择
go test ./internal/bootstrap/... -count=1    # 含装配与端到端（真实引擎 + 替身服务）
build.cmd verify                             # 仓库闸门（build + vet + 短测）
```

| 用例 | 覆盖 |
| --- | --- |
| `TestEmbeddedWriteSearchListDelete` | 写入往返、**幂等去重**、词法排序、删除与重复删除 |
| `TestEmbeddedIsolatesUsersInSameFile` | 同一个库文件下不同 `user_id` 互不可见 |
| `TestBackendSelection` | `backend` 留空/显式/未知值的推断与校验 |
| `internal/memory/client_test.go` | mem0 HTTP 契约（含"只发 X-API-Key"） |
| `internal/bootstrap/memory_e2e_test.go` | 装配后的真实链路（含默认关闭时完全无副作用） |

**未验证项（如实标注）**：进程内后端的**真实工作台端到端**（起一次带 LLM 的完整对话、
观察召回注入）需要在有可用模型服务商的环境里跑；本仓库的自动化测试覆盖到装配与后端
行为这一层，没有覆盖"真实模型 + 真实对话"的召回效果。

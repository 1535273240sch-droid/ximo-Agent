## 一、P1 问题与修复（7 个，全部已修）

### 1. 【任务3】阶段事件用了会被剥掉载荷的通道，且验收测试失败（阻塞门禁）
- 现象：`build.cmd verify` 基线即失败——`TestExpertRunEmitsPhaseEvents` 拿到 0 条阶段事件。
- 根因：`expert_run.go::emitExpertPhase` 把阶段信息挂在 `EventProgress` 上。合并器
  （`backpressure.go::flushKey`）重建合并帧的 Data 时只保留 content/reasoning，
  `phase` 载荷被静默剥掉；且 progress 不落库，断线重连后阶段不可见。测试期望的是持久事件。
- 修复：阶段跃迁改发持久的 `EventRunStateChanged`（State=thinking，Data 带
  phase/expertId/expertName/plan）。前端对该事件只更新状态不读 Data，恢复逻辑兼容 thinking 态，
  阶段从此可持久回放。

### 2. 【任务5】指定候选顺序含失效 ID 时，健康候选被整体浪费
- 现象：设置面板的按专家/分类分配残留了已删除服务商的 ID 时，`Pool.Select(order)` 在 order 全部
  未命中池内候选时直接返回 false，子代理报「模型池中没有可用候选」，即使池里还有健康候选。
- 修复：`pool.go::Select` —— order 里**没有任何**池内候选时回退池默认顺序；混有真实 ID 时仍按
  pinned 语义优先真实候选。新增回归测试 `TestPoolSelectFallsBackWhenOrderUnknown`。

### 3. 【任务5】API 调用中途到期的子代理超时被误判为「可转移」
- 现象：轮次边界的超时正确归一为 `ErrSubAgentTimeout`（不转移），但 API 调用**进行到一半**到期时
  provider 返回裸 `DeadlineExceeded`，被错误分类归为「连接超时」→ 触发失败转移，每个候选把整个任务
  从头重跑（最坏 N×超时上限），与「超时不转移」的自述口径矛盾。
- 修复：`subagent.go` 两处 Complete 失败路径在 `runCtx.Err() != nil` 时归一为 `ctxErr(runCtx, ctx)`
  （超时→ErrSubAgentTimeout，取消→原样透传）。新增回归测试 `TestSubAgentNoFailoverOnMidCallTimeout`。

### 4. 【任务5×任务3 集成缺口】用户手选专家路径绕过模型池与 expert_agent 闸门
- 现象：验收标准 3「同时在跑的子代理数 ≤ 8」只在不可达的 `App.ExpertOrchestrator()` 路径成立；
  当前唯一可达的用户手选专家路径（engine 直连 `executeExpertRun`）既不走池/失败转移，也不占
  `expert_agent` 槽位。
- 修复：`engine.Dependencies` 新增 `SubAgentPool`（取池函数，惰性+失效重建）与
  `SubAgentCandidates`（按专家/分类的候选顺序）两个可选注入；`newExpertOrchestrator` 接入共享
  ResourcePool（`e.Scheduler().Resources()`，与工具/agent_expert 路径同池）与候选池。未注入（测试）
  时行为与原来完全一致；bootstrap 已完成装配。

### 5. 【任务4】引擎重启后确认计划，已批准的计划被静默丢弃
- 现象：run 停在计划确认时进程重启 → 恢复路径 rehydrate 出的合成请求 `PlanMode=false` → 用户点确认后
  decision 被消费，但 loop 因无 flag 跳过计划分支，run 以占位 prompt 重新执行，批准的计划既不注入也不执行。
- 修复（两处）：
  1. `engine.executeRun`：`decision != PlanDecisionNone` 时给 loop 请求显式置 `PlanMode=true`
     （engine 是唯一合法决策来源，不破坏 loop 层防注入设计）；
  2. `engine.applyRecoveryPlan`：已停在 waiting_user 的 run 重启后同态迁移会报
     「already in waiting_user」导致恢复 Notes 出现 apply failed 噪音——机内已在 waiting_user 时跳过
     迁移、直接重录 park。
  新增端到端回归测试 `TestPlanApprovedAfterRestartStillExecutes`（重启→Recover→确认→按批准计划执行完）。

### 6. 【任务2】权限面板陈旧快照整体写回，可能回滚其他面板刚保存的配置
- 现象：PermissionPanel 用挂载时的一次性快照整体 applySettings 写回；用户先在「子代理模型分配」保存过，
  再切一次权限模式，子代理配置被静默回滚。
- 修复：写回前先 `getSettings()` 取 fresh，仅覆盖 `auto_mode`（对齐 SubAgentModelPanel 的既有正确做法）。

### 7. 【任务2】权限模式「即时生效」的文案与实际链路不符（安全感知落差）
- 现象：面板注释与设置页 hint 宣称切换即时热重载；实际链路只落盘 config.json，运行中的引擎进程仍按
  启动时模式放权（yolo→safe 切换后工具继续全放行直到重启）。
- 修复：先修文案（hint 改「已写入配置文件，重启应用后生效」，注释同步更正）。热重载需要重建 tool
  runtime 适配器，涉及引擎运行态重建，留作后续项（见 P2 清单第 1 条）。

### 8. 【任务3×任务4】专家+计划同时设置时 plan_mode 被静默忽略（前端补互斥）
- 说明：后端「专家路径忽略 plan_mode」是任务 3 有测试固化的组合规则
  （`TestExpertRunIgnoresPlanModeInteraction`），问题在前端允许同时提交且无感知。
- 修复：Composer 选中专家时同步关闭并禁用计划开关（带提示文案），提交 payload 双保险
  （`plan_mode` 仅在未选专家时携带）。`PlanModeToggle` 最小扩展可选 `disabled/disabledTitle` props。

## 五、追加修复（2026-09-25 晚）：第三方模型地址「获取不了模型 / 保存不了」

用户实测发现设置页第三方接口处获取模型失败、保存无效。探针直连运行中的后端复现并定位到三个叠加原因，均已修复并实测：

1. **后端出网不走系统代理**（主因）：Go 默认 Transport 只认环境变量代理，而 Electron spawn 的子进程
   不继承系统代理 —— 直连 api.openai.com 这类地址 20s 超时。修复：新增 `internal/provider/proxy.go`
   （共享代理感知 HTTP 客户端：环境变量 → Windows 系统代理 → 直连；回环地址永远直连），
   `proxy_windows.go` 读注册表 ProxyEnable/ProxyServer（30s TTL，支持按协议形态），chat/completions
   与模型列表共用。
2. **「获取模型」查的是已保存地址而非表单当前值**：改了地址没保存就点获取，报错与所填地址无关。
   修复：`system.model.list` 帧支持可选 `base_url`，前端「获取模型」带表单当前地址。
3. **坏 URL 被静默保存**（如手滑漏了 https://）：之后所有请求以隐晦方式失败。修复：新增
   `config.NormalizeBaseURL`（补 https://、去尾斜杠、校验协议与主机名），保存与拉取两处统一规整，
   规整不了报人话错误。

验证：`build.cmd verify` 全绿（含压测，回环直连规则修正了压测里本地 mock 被误送代理的问题）；
探针实测 —— 修复前 `api.openai.com` 20s 超时，修复后返回 HTTP 401（请求真实到达，401 是密钥与
该地址不匹配，属预期）；本地 mock 拉取与坏 URL 规整用例均通过。已重新打包 dist 并就地更新
桌面软件（后端 exe + asar），运行中的实例实测通过。

## 六、追加修复（2026-09-25 晚，续）：「一点保存，模型和请求链接立马回退」

用户继续实测发现：保存后表单立即回退到旧值。根因与凭据面板/候选池面板的**双源覆盖**有关：

- `providers[0]`（候选池首位=主服务商）与顶层 `base_url/model` 指向同一份数据；凭据面板只编辑
  顶层（providers 是它读到的旧快照），候选池面板只编辑 providers（顶层是旧快照）。
- 任务5 后端合并时让 `providers[0]` 无条件胜出 → 凭据面板的保存被旧快照原样顶回（base_url、
  model、**新保存的密钥引用**全部回退），界面表现为「一点保存就回退，然后用不了」。

修复（`internal/bootstrap/secrets.go::ApplySettings`）：候选池合并改为**逐字段取「与当前落盘值
不同的那一侧」**（即谁改过用谁，两侧都改则顶层优先），主服务商在合并后一次性落位。新增回归测试
`TestApplySettings_SaveNotClobberedByStaleProvidersSnapshot` 覆盖三个场景：凭据面板保存不回退、
候选池面板编辑不丢、新密钥引用不被顶掉。

验证与部署：`build.cmd verify` 全绿；对运行中的正式实例探针实测「改地址→保存→读回」不再回退，
且用当前配置拉取模型成功返回真实列表（经由系统代理）。dist 与桌面软件均已更新（app.asar 无需
重打包——本项为纯后端修复）。

## 七、追加修复（2026-09-25 晚，二）：输入框模型列表 / 候选池自动添加 / 流式输出 / 计划交互

用户反馈四个问题，排查结论与处置：

1. **输入框「默认模型」下拉没有其他模型** —— 是第三方地址连不通（见第五节）的连带症状。
   代理与保存修复后已实测恢复：下拉打开即拉取当前配置的模型列表（含错误提示与「重新获取」）。
2. **候选池不能自动获取模型**（此前要手动复制粘贴模型名）—— 在子代理面板新增「**自动获取候选**」：
   一键向主服务商拉取模型列表（用首行当前填写的地址，无需先保存），勾选后批量生成候选行
   （已存在的模型自动跳过），点「保存分配」生效。纯前端改动。
3. **没有流式输出** —— 排查结论：**流式链路本来就是通的**（loop 的 OnDelta → providerAdapter SSE
   直通 → coalescer 合帧 → 前端 1s 排空渲染）。对运行中实例真实提交 run 实测：23 帧 token.delta、
   时间跨度 1.1s，真流式。本次补了两处小改：长任务收尾轮（forceWrapUp）也接上 OnDelta 保持流式；
   输入框的四个选项状态提升到全局 store（见下条）。短答案的增量会在几百毫秒内到达完毕，观感接近
   一次性输出属正常。
4. **「遇到复杂问题的弹窗交互」（计划模式）** —— 链路逐环核验健康：开「计划」开关提交 → 后端先出
   计划 → 聊天流底部出现**内嵌的计划确认卡片**（不是系统级模态弹窗）→ 确认/拒绝后继续。找到并修复
   一个真实漏网路径：空会话的「建议探索场景」按钮此前直接提交、**绕过计划开关**（复杂任务点场景必
   不出计划卡）——已把输入框的计划/GO/模型/专家四个选项提升到全局 store，场景按钮与手动发送走
   同一套选项。注意：计划模式与专家选择互斥（专家自带方案阶段，设计如此）。

验证：`build.cmd verify` 全绿 + 前端两套 tsconfig typecheck 通过；dist 与桌面软件均已更新并重启，
运行实例流式实测通过。

# 接口裁决记录（第 32 章 / 第 08 号任务第二步）

本文件是 08 号主 Agent 对 01～07 号任务书里「需要主 Agent 裁决的公共类型」小节的逐条裁决结果，
以及裁决所依据的规则。所有裁决已落到 `internal/types/`，并配有可执行断言
（`internal/types/contract_test.go`），后续任何模块任务若与契约不一致，测试会失败。

**裁决原则（来自 08 号任务书第二步）**：「少改调用方多改定义方」——谁的类型被更多方消费，
谁的字段命名优先保留。当两条原则冲突时，以架构文档为准；本次裁决期间架构文档不在本机也不在
v1 仓库内（见 `集成报告.md`「输入缺失」），因此凡任务书之间互相矛盾之处，一律取**被消费方最多、
且与任务书引用章节一致**的一方，并在下面显式标注依据。

## A1 — `Event` 的字段与归属

**登记内容**（03 号任务书末尾）：*「`Event` struct 的字段（event_id/type/payload/seq等）需要和任务 02 里
Engine 用的 Event 类型对齐，建议本任务先定义，02 号直接复用本任务的类型定义。」*

**裁决：采纳 03 的定义，并把类型从 03 的包挪到 `internal/types/event.go`。**

- 字段与任务书第 03 号「run_events 表结构（第 9.1 章，直接照抄）」一一对应：
  `RunID / Seq / EventID / Type / PayloadJSON / CreatedAt`，JSON tag 与列名完全相同，
  使同一 struct 既能走 append 路径也能走 replay 路径，不需要中间转换层。
- 归属挪走的理由：02（Engine 写事件）、04（工具运行时写事件）、06（Provider 埋点关联 run）
  都要引用它，03 是定义方但不再是唯一持有方；若留在 03 的包，02/04/06 必须 import 存储包，
  与「存储是被依赖的底层」方向一致但会把「类型」和「存储实现」绑死。放进 `internal/types` 后
  该包不 import 任何 internal 包，是叶子节点，循环依赖在结构上不可能出现（第八步要核对的
  「04 依赖 03 的 Event、03 又依赖 04 的某个类型」正是这么消掉的）。
- 附带按第 7 章补上 `EventClassOf` / `IsDurable`：durable（必须保留）与 coalescible（可合并）
  两级。边界事件清单见 `event.go` 常量，未知类型**默认 durable**——把未识别的类型当可合并而
  丢掉一个边界事件，比多留一条事件的代价大得多。

## A2 — `internal/context` 的包名（08 在拼目录时发现）

第 31 章目录树里是 `internal/context/`，但若包名叫 `context`，02 号（Agent Loop、Engine）在
任何同时使用标准库 `context` 的文件里都会遮蔽它——标准库 `context` 是本项目每一层签名都在用的
（`Engine.Submit(ctx context.Context, ...)` 等），遮蔽后果是整包编译错误，且报错信息指向一个看起来
完全正确的 import。

**裁决：目录名保持 `internal/context/`（与第 31 章一致，不擅自改结构），包名定为 `contextmgr`。**

这是「少改调用方」的直接应用：02/06 的任务书都写的是 `internal/context/` 路径，改目录名会让两份
任务书的交付物清单全部对不上；而包名只在 import 后的引用处出现，改包名不影响任何路径。

## A3 — `RunState` 与 01 号恢复扫描的措辞冲突

**登记内容**（01 号任务书第 3 条）：*「scan runs where status ∈ {running, executing, waiting_worker}」*；
**02 号任务书**给出的却是第 4 章枚举
`created/queued/planning/thinking/executing/compacting/waiting_user/completed/cancelled/failed/recovering`。

两者没有公共字面量：`running` 和 `waiting_worker` 在 01 的枚举里根本不存在。

**裁决：以第 4 章枚举为唯一权威（采用 02 的 `RunState`），01 号改用谓词判定，不得再按字符串列表扫描。**

- 第 4 章是规范来源，且 01 那句是恢复算法伪代码里的口语描述，不是类型定义。
- 映射关系固定为：
  - `running` → `{planning, thinking, executing, compacting}`
  - `executing` → `executing`
  - `waiting_worker` → `executing`（等 worker 租约的 run 仍处于 executing，不会因为等租约而离开该状态）
- 已提供 `RunState.IsRecoverable()` 作为替代判定，并有专门的回归测试
  `TestRunStateRecoverableCoversSupervisorScan`：**01 那个集合里的每个状态都必须满足
  `IsRecoverable()`**，否则重启后会静默跳过需要恢复的 run——这是最危险的一类集成缺陷（不报错、
  只是任务永远卡住）。
- `RunState("running").Valid()` 返回 false，并有 `TestRunStateValidRejectsUnknown` 兜底：
  写入 runs 表前的校验会挡住任何沿用了旧词汇的调用方。

## A4 — `FrameHeader` 的归属

**登记内容**（01 号任务书末尾）：*「`FrameHeader` 是否放进全局共享的 `internal/types` 还是留在
`internal/ipc` 由各方 import——建议登记但先按上面签名开发。」*

**裁决：挪入 `internal/types/ipc.go`，字段与 01 号签名完全一致（零字段改动）。**

- 消费方是 02（Engine RPC）与 05（worker 协议），生产方是 01。留在 `internal/ipc` 会让 Engine 和
  Worker 两个包为了引用一个头部结构而 import IPC 传输包，把 01 依赖 02/05 的方向反转成
  02/05 依赖 01 的传输层——这正是 Supervisor 架构要避免的耦合。
- 因为字段一个没改，01 只需把 `ipc.FrameHeader` 改成 `types.FrameHeader`，是纯 import 路径调整，
  与 01 任务书自己的预判一致（「如需挪包只是改 import 路径，不影响逻辑」）。
- 08 顺带补齐了协议的两个硬约束，二者都是「缺了会出安全问题」而不是风格问题：
  - `MaxFramePayload`（64 MiB）：声明长度超限的帧在**分配内存前**就被拒绝，避免伪造的长度字段
    直接打爆内存；
  - `Validate()` 拒绝版本不一致的帧而非尽力解析——Supervisor 链路上的版本不匹配不能靠猜恢复。
- 帧类型枚举（`FrameRunSubmit` 等）按 01 任务书的提示，以 v1 九个 IPC 子模块（chat/computer-use/
  data/fs/misc/network/skill/system/update/window）为分组参考起点重新定名。

## A5 — `CompletionRequest/Response` 与 02/07 的对齐

**登记内容**（06 号任务书末尾）：*「`CompletionRequest/CompletionResponse` 的字段，尤其是流式 chunk
的结构，需要和任务 02 的 Agent Loop、任务 07 的 Observability 指标埋点对齐命名。」*

**裁决：以 `RunID / TurnID / RequestID / Attempt` 四元组作为三方的对齐锚点。**

- 这四项正是第 06 号任务书第 1 条要求的 *「每次请求要记录 `request_id/run_id/turn_id/attempt`
  写入日志」*，因此它不是我新增的约定，而是把 06 自己已写明的字段提升为跨模块契约。
- 对齐语义固定下来，避免 02 与 07 各自解释：
  - `RequestID` 每次 attempt 都**新生成**；重试时 `RunID/TurnID` 不变、`Attempt` 递增。
    这样 `provider_retry_total` 可按 `Attempt>1` 统计，而 `provider_latency_ms` 能归属到同一个 turn。
  - `Emitted`（对齐 06 任务书里 v1 的 `emitted` 标志）用于第 18 章「零输出才可重放」的判断。
  - `TokenUsage.CachedPromptTokens` 单独计数：前缀缓存命中率是「字节稳定前缀」设计的首要指标，
    混进 `PromptTokens` 会导致这项优化彻底不可观测。
- 流式侧 `StreamChunk` 用 `Kind` 判别（content/reasoning/tool_call/usage/done/error），
  并保留 `ToolCallIndex` 以支持并行工具调用的交错流；`StreamChunk` 属于 coalescible 流量，
  可被 02 的背压合并，不属于 durable event。

## A6 — `ToolRequest` ⇄ `WorkerRequest` 转换的归属空档

**登记内容**：04 号任务书末尾 *「`ResultNormalizer.Normalize(raw WorkerResponse) (ToolResponse, error)`」*；
05 号任务书末尾 *「`WorkerRequest/WorkerResponse` 的字段需要与任务 04 的 `ToolRequest/ToolResponse`
做一次映射约定，08 号统一检查两边的转换代码（Result normalization）是否对得上。」*

**问题**：04 期待拿到消化的 `WorkerResponse`，05 期待 04 提供 `ToolRequest` 的映射——两边都以为
对面在做转换，实际是空档。这正是 08 任务书第二步点名要检查的项。

**裁决：两侧契约类型分开保留，转换函数落在 `internal/types/worker.go`，由 08 定义、双方共同消费。**

- `ToolRequest/ToolResponse`（04 拥有，面向 Engine）与 `WorkerRequest/WorkerResponse`（05 拥有，
  面向进程边界）**故意不做成同一个类型**：前者是模块内契约，后者是跨进程传输契约，混用会让每次
  传输层演进（加重试元数据、排队信息）都波及全部工具实现。
- `BuildWorkerRequest(req, kind, attempt)` —— 出站方向。三条拒绝规则都对应真实故障：
  - 缺 `ToolCallID`/`ToolName` 拒绝（否则响应无法归属）；
  - 非 worker 域工具拒绝（把纯 Go 工具送过进程边界，等于悄悄把它降级到更弱的故障域，
    与 04 的路由决策矛盾）；
  - `attempt < 1` 拒绝（第 0 次尝试无法与「重放」区分）。
  - 空参数补成 `{}` 而非留 nil：worker 反序列化 nil 会报错，而不是得到一次空调用。
- `NormalizeWorkerResponse(resp, opts)` —— 入站方向，分支顺序即语义优先级：
  1. worker 成功 → `completed`，**但 `Durable` 保持 false**；
  2. 超时 → `timeout`（超时压过幂等分类，它是独立结局而非普通失败）；
  3. 失败且属 C 类非幂等 → `needs_confirmation`；
  4. 失败且属 A/B 类 → `failed`（允许重试）。
- 第 1 条与第 3 条是关键：
  - **`Durable` 只能由存储提交置位**（I3）。worker 报成功不等于已提交；若转换阶段就把 Durable 置 true，
    就会造出「引擎认为工具已完成、DB 里没有结果」的中间态，正是第 9.2 章要杜绝的。
  - **C 类失败不留重试余地**（I8）。worker 失败点未知，副作用可能已发生，重新执行会双写；
    因此必须停成 `needs_confirmation` 交人判断，而不是当普通失败交给上层重试。
    对应测试 `TestNormalizeNonIdempotentFailureNeedsConfirmation`。
- 另按第 19 章把幂等三分类 A/B/C（`Idempotent/Detectable/NonIdempotent`）也收进契约，
  因为 02 的恢复逻辑直接消费它却由 04 判定。
